迴圈工程 (Loop Engineering) 的本質

迴圈工程是把「負責提示 AI 的工程師自己」這個角色，換成一套替你完成此工作的系統。你只設計這套系統一次，之後它就持續運轉，代替你進行手動提示、驗證和修正。

🔄 迴圈的五個關鍵階段 (The Loop Lifecycle)

探索 (Discover) → 規劃 (Plan) → 執行 (Execute) → 驗證 (Verify) → 迭代 (Iterate)。
這套回饋循環是自動的。通過驗證就提交 (Commit)，沒通過就自動再跑一輪，直到完美通過。

槓桿轉移： 開發者的工作從「打字下提示」提升為「設計那套會自己下提示並驗證的迴圈系統」
核心能力與思維對照
提示工程 (Prompting) 語言與表達導向

追求「更好的單次輸出」，人是回饋迴圈的核心，每次輸出皆需手動除錯。口號是：「幫我寫一個函式」。

迴圈工程 (Looping) 軟體工程與自動化

追求「可靠且已驗證的結果」，系統自檢自修。口號是：「寫出程式碼、自動測試、修到通過為止」。

CHAPTER 02 / 迴圈工程的六大核心技術組件
PAGE 03 / 05
1. 自動化 (Automations)

迴圈的心跳。定義提示與頻率讓代理定時重跑，例如在 Claude Code 中使用 /loop 或 /goal 讓代理持續修改，直到指定的所有測試全數通過才停下。

心跳頻率與目標導向
2. 工作樹 (Worktree)

環境與資源隔離。利用 git worktree 機制為每個平行運作的代理分配獨立的分支與專屬目錄，避免多個 AI 代理同時修改同一檔案產生程式衝突。

平行開發與衝突隔離
3. 技能 (Skills)

專案脈絡的知識複利。在資料夾下放置 SKILL.md 純文字檔，記錄專案習慣、指令、地雷和建置步驟。避免代理每次啟動都得從零摸索。

專案上下文與經驗固化
4. 外掛與連接器 (Connectors)

工具觸達。建立在 MCP (Model Context Protocol) 協定上，讓代理能夠讀取 Jira/Linear 待辦、查詢資料庫、戳 API 測試環境，自動開 PR 並於 CI 跑過後在 Slack 發通知。

協定互通與工具控制
5. 子代理 (Sub-agents)

獨立驗證與評估（Evaluator-Optimizer）。寫程式的代理往往對自己太過寬容，引入另一個獨立的子代理進行批改與代碼審查，才能確保產出代碼的客觀真實性。

多模型評估者-優化者模式
6. 記憶 (Memory)

跨次狀態保存。將任務進度（已完成、待完成）記錄在 Markdown 狀態檔或 Linear 看板上。代理會隨著對話結束而失憶，但 Git 倉庫與檔案系統永遠記得。

檔案級持久化狀態保存

最小可行性迴圈 (MVP) 的 4 個零件

1. 自動化與排程

依照指定週期觸發，或在達到明確的目標條件時自動停止的機制。

2. 技能手冊 (SKILL.md)

固化專案慣例、除錯歷史、建置和測試的特定命令指引。

3. 進度狀態檔

利用一個 Markdown 檔記錄「做了什麼、還剩什麼」，方便明天續跑。

4. 客觀關卡 (Gate)

測試是否通過、型別檢查 (linter)、編譯成功否。此決定迴圈是幫你還是燒錢。

我需要建迴圈嗎？四個硬性指標

多數開發者現階段不需要迴圈。必須同時符合以下四點，迴圈的建置成本才划算：

1
高度重複性
任務至少每週發生一次，可用多次執行攤平前期建置成本。一次性任務用好提示即可。
2
能 100% 自動化驗證
必須有「沒有你在場也能自動判定成果不及格」的關卡（如單元測試、編譯器）。
3
Token 預算足夠
迴圈會反覆讀寫、探索與重試，不論結果都會燒大量 token（單次可達 5 萬至 20 萬 token）。
4
資深開發者級除錯工具
代理必須能查看完整日誌（Logs）、能在沙盒中跑代碼，並擁有完整的測試除錯環境。

CHAPTER 04 / 迴圈無法幫你扛的三個風險與結論
PAGE 05 / 05

隨著迴圈越做越好，將越尖銳的三個問題

1. Ralph Wiggum 迴圈
無聲失敗 (Silent Failure)
代理在完成任務前，錯誤發出「已完成」信號，導致迴圈退出而停在半成品，還繼續燒 token 預算。
解法：設定嚴格客觀的 Gate 驗證
2. 理解債 (Comprehension Debt)
代碼庫失控
迴圈以極速交付你沒寫過的代碼。當落差擴大，某天系統壞掉，除錯成本暴增。
解法：堅持閱讀與理解每一行 diff
3. 認知投降 (Cognitive Surrender)
喪失自主判斷
因為迴圈全自動跑，開發者容易全盤接受其回覆。迴圈分不出優劣，但工程師必須分得出。
解法：保持批判性與自我程式素養
警告: 跳過手動測試直接上迴圈，是在正式環境翻車的主因。 評估指標: 每個被採納的修改花費了多少成本，而非燒了多少 token。

🎯 迴圈工程師的實踐策略

建設迴圈的正確順序：

第 1 步：穩定單次手動
先讓「手動一次執行」的提示詞與流程穩定。
第 2 步：固化為 Skills
將脈絡存入 SKILL.md，防止每次重讀。
第 3 步：包裝迴圈並排程
配置自動關卡後，才交由迴圈系統自主運行。
