迴圈工程典範轉移：從手動提示到自主開發系統

開發者正在把工作重心從「單次下提示」轉向「設計能自己跑測試、自己修錯的自主迴圈」。這篇筆記拆解迴圈系統的六個核心組件、最小可行架構，以及導入前該守住的四項門檻與三道風險防線。

核心脈絡：從單次提示轉向自主迴圈系統

2026 年的開發工作流出現一個明顯變化：工程師不再只靠手動輸入提示詞來換取單次輸出，而是改為設計能自行檢查與修正的程式迴圈。開發者把過去反覆下指令與人工驗收的工作，交給系統按規則持續執行。

"You shouldn't be prompting coding agents anymore. You should be designing loops that prompt your agents."

Peter Steinberger (OpenAI) / Boris Cherny (Anthropic)

這套做法稱為迴圈工程（Loop Engineering）。開發者只要訂好一次系統規則，代理程式（Agent）就會自動重複五個階段：探索（Discover）、規劃（Plan）、執行（Execute）、驗證（Verify）與迭代（Iterate）。系統通過客觀測試才會提交變更；沒通過就自動重修，直到符合所有預設條件。

底層機制：六大核心組件與最小可行架構

光靠大型語言模型（LLM）的單次推理能力，撐不起穩定的自主寫程式迴圈。一套能長期運作的系統需要六個基礎組件，各自負責排程、環境隔離、知識傳承、工具存取、客觀審查與跨次記憶。

自主迴圈的六大核心組件

  • 自動化（Automations）：負責排程與觸發。設定執行頻率與停止條件（如 Claude Code 的 /loop 或 /goal）後，代理就會持續改寫程式碼，直到指定測試全數通過。
  • 工作樹（Worktree）：負責隔離環境與檔案。git worktree 會為平行運作的代理配發獨立分支與專屬目錄，避免多個代理同時改同一份檔案而衝突。
  • 技能（Skills）：累積專案脈絡的說明文件。在專案目錄放入 SKILL.md 純文字檔，記下團隊慣例、建置步驟、常用指令與已知錯誤，代理每次啟動就能直接套用。
  • 外掛與連接器（Connectors）：連接外部系統的介面。透過模型上下文協定（MCP，Model Context Protocol），代理能讀取 Jira 或 Linear 任務、查詢資料庫並測試應用程式介面（API）。持續整合（CI）通過後，代理還能自動開啟合併請求（PR）並發送 Slack 通知。
  • 子代理（Sub-agents）：負責獨立驗證與審查。單一代理容易對自己寫的程式碼過度寬容。導入「評估者與優化者（Evaluator-Optimizer）」模式後，獨立子代理會接手代碼審查與批改，擋下瑕疵。
  • 記憶（Memory）：保存跨工作階段的進度。對話記憶會在工作階段結束時清空，團隊必須把已完成與待辦項目寫進 Markdown 狀態檔或 Linear 看板，靠檔案系統與 Git 倉庫留下長期紀錄。

最小可行性迴圈（MVP）的四項基礎零件

實務上建置迴圈不必一次到位，靠四個最小可行產品（MVP）零件就能運轉：

  • 自動化排程：依固定週期觸發任務，或依目標條件自動停止。
  • 技能手冊：在 SKILL.md 記錄專案慣例與測試指令，讓代理照章行事。
  • 進度狀態檔：用 Markdown 記下當前進度，讓隔天或下次啟動直接接續。
  • 客觀關卡（Gate）：靠單元測試、型別檢查與編譯驗證判定成敗；沒有這道關卡，迴圈只會空轉並燒光運算資源。

決策矩陣：思維對照與導入評估標準

轉向迴圈工程後，開發者的重心不再是琢磨單次指令，而是設計系統規則與驗證標準。下表對比兩種工作模式的差異，幫團隊看清轉型的實際邊界。

比較維度 提示工程（Prompting） 迴圈工程（Looping）
核心導向 語言表達與指令微調 軟體工程與系統自動化
追求目標 取得更好的單次生成結果 產出可靠且通過驗證的成果
回饋機制 人類作為回饋核心，每次手動除錯 系統依客觀關卡自動檢查並重試
開發者角色 直接下達步驟的操作者 設計迴圈規則與驗證標準的架構師
典型指令 「幫我寫一個函式」 「寫出程式碼、自動測試、修到通過為止」

現階段不必把所有開發任務都搬進迴圈系統。前期建置與除錯都要花費工程成本，任務必須同時符合這四項門檻，導入迴圈才划算：

評估指標 合格門檻 實務考量與成本說明
高度重複性 至少每週發生一次 必須靠高頻率執行來攤平建置成本；一次性任務維持手動提示即可。
100% 自動化驗證 具備無人值守的及格判定關卡 需有單元測試、編譯器或靜態檢查工具，能客觀判定成果是否通過。
Token 預算充足 能負擔單次 5 萬至 20 萬 token 迴圈會反覆讀寫檔案、探索與重試，無論最終是否成功都會持續消耗 token 額度。
完整除錯環境 具備沙盒與完整日誌存取能力 代理必須能讀取完整執行日誌（Logs），並在獨立沙盒中執行測試與除錯。

風險邊界與工程師的實踐策略

迴圈跑得越快，出錯時的破壞半徑也越大。全自動流程替代不了人類的系統判斷力，團隊必須先針對這三個失效模式設好防線。

迴圈系統無法代勞的三項風險

  • Ralph Wiggum 迴圈（無聲失敗）：代理在任務還沒收尾時誤判並發出「已完成」信號，讓迴圈提早結束、留下半成品並白白燒掉預算。解法是把嚴格且客觀的自動化關卡（Gate）設為唯一退出條件。
  • 理解債（Comprehension Debt）：迴圈能持續產出開發者沒親手寫過的程式碼。團隊對系統的掌握度一旦落後，日後故障時的除錯成本就會成倍增加，工程師仍須讀懂每一行程式碼差異（diff）。
  • 認知投降（Cognitive Surrender）：系統產出越順暢，開發者越容易放棄把關而直接照單全收。迴圈分不出架構好壞，工程師不能交出批判思考與程式設計的判斷權。

導入迴圈的正確順序與成本指標

導入迴圈不能跳級，照這三個步驟推進才不會在正式環境釀成事故：

  1. 先穩定手動流程：確認單次手動提示與工作流程能穩定產出正確結果。
  2. 固化專案知識：把除錯經驗與專案脈絡寫進 SKILL.md，省去代理每次重新摸索的成本。
  3. 接上關卡與排程：最後才配置自動化關卡與排程，讓系統接手自主運行。

評估迴圈系統的投資報酬率（ROI）時，該追蹤「每個被採納的修改花多少錢」，而不是只看總共燒了多少 token。系統寫出的程式碼能穩定通過審查並合入主線，這套架構才算真正站得住腳。
