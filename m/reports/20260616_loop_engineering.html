迴圈工程 (Loop Engineering) 的興起：從撰寫提示詞到設計自主寫程式迴圈

解析 2026 頂尖工程師為何不再寫提示詞，而是設計「會自己迭代、自檢、自我修復」的 AI 寫程式迴圈。拆解六大組件與三大風險。

MODULE 1

概念對照：提示工程 vs 迴圈工程

從「給代理一道指令」到「給代理一份工作」
迴圈工程的定義

把「負責提示 AI 的你」換成一套自動執行、檢驗並迭代的系統。你只設計這套系統一次，之後它就自主運轉。

概念演進與差異
  • 提示工程 (Prompting)：語言能力導向。單次輸出，手動除錯，人是回饋迴圈。口號是「幫我寫一個函式」。
  • 迴圈工程 (Looping)：軟體工程導向。系統自跑、自檢、自修。口號是「寫出程式碼、自動測試、修到通過為止」。
MODULE 2

迴圈工程的六大核心組件

支撐自主寫程式的六大技術支柱
1. 自動化 (Automations)

迴圈心跳。定義提示與頻率，讓代理持續重跑（如 /loop 或 /goal），直到指定測試全數通過。

2. 工作樹 (Worktree)

環境隔離。透過 git worktree 給每個代理分配獨立的分支與目錄，防止多代理平行運作時產生代碼衝突。

3. 技能 (Skills)

經驗固化。透過 SKILL.md 固化專案慣例、除錯歷史、建置和測試命令，避免代理每次重啟都重新熟絡專案。

4. 連接器 (Connectors)

工具觸達。利用 MCP 協定，讓代理直接存取 Jira/Linear 看板、查詢資料庫、戳 API，並在 Slack 上拋通知。

5. 子代理 (Sub-agents)

評估與優化（Evaluator-Optimizer）。引入獨立子代理進行客觀審查，打破原代理「對自己代碼太過寬容」的盲點。

6. 記憶 (Memory)

狀態保存。將任務進度（已做/待做）寫入 markdown 或 Linear。對話會結束，但 Git 倉庫永遠保存記憶。

MODULE 3

MVP 零件與實施評估

我需要建迴圈嗎？最小可行性評估
最小可行迴圈的 4 個零件
  • 自動化與排程：遇到明確條件就停的排程執行。
  • 技能 (SKILL.md)：存放專案脈絡，避免重新摸索。
  • 狀態檔：以 markdown 檔記錄進度，讓明日「續跑」。
  • 客觀關卡 (Gate)：自動擋下爛輸出的測試或型別檢查。
實施迴圈的 4 個硬性條件
  • 重複性：這件事至少每週重複發生一次。
  • 驗證可自動化：擁有「沒有你在場也能判定不及格」的客觀指標（如測試）。
  • Token 預算足夠：迴圈會反覆讀取與探索，極燒 Token（單次 5~20 萬）。
  • 資深開發者級工具：代理具備 logs 檢視與代碼執行環境。
MODULE 4

迴圈不會幫你扛的三個風險

隨著迴圈成熟，越尖銳的人為挑戰
1. Ralph Wiggum 迴圈 (無聲失敗)

代理在出錯或半成品狀態下，錯誤發出「已完成」信號使迴圈退出，導致無聲失敗並持續燒 token。必須有客觀 Gate 擋下。

2. 理解債 (Comprehension Debt)

迴圈交付代碼太快。當你和倉庫裡的真實代碼落差過大，未來除錯代價將極度慘痛。唯一解法：堅持親自閱讀 diff。

3. 認知投降 (Cognitive Surrender)

自動化跑起來後，開發者容易放棄自主判斷，全盤接收代理拋回的產出。迴圈分不出好壞，但工程師必須分得出。

MODULE 5

迴圈工程師的實踐步驟

如何務實、循序漸進地建立你的寫程式迴圈
循序漸進的建置順序
  • 第 1 步：穩定單次手動。先讓單次指令的輸出穩定、可靠。
  • 第 2 步：包裝技能。寫好 SKILL.md，將探索過的脈絡與地雷規律固化下來。
  • 第 3 步：建立迴圈與自動 Gate。當有了 100% 可信賴的測試或編譯驗證機制後，才開放給迴圈自動化運行與排程。
結論與思維

「建你的迴圈，但要像一個打算『繼續當工程師』的人那樣建，而不是只當那個按下執行鍵的人。」
